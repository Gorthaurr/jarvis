## Что это
Голосовой ИИ-ассистент-мажордom («Джарвис» у Старка) для ОДНОГО пользователя на его Windows-ПК.
Слышит речь → понимает намерение → **управляет компьютером инструментами** → отвечает голосом.
**Мозг — облачный Claude:** слабый тир Sonnet 4.6 (дефолт ходов), эскалация на Opus 4.8 при застревании
(§7-каскад, 2026-06-23). Тонкий клиент + облачные нейро-сервисы (STT/TTS/LLM).

### КОНЦЕПЦИЯ (критично для любых правок)
- **НЕ хардкодить шаги под сценарии.** Даём мощные, надёжные, ЧЕСТНЫЕ инструменты — модель сама
  хорошо ими пользуется. Актуатор резолвит из источников истины ОС и честно сообщает провал; что
  не вышло — модель добирает сама (`web_search`/`code_run`).
- **Честность по ошибкам — закон.** Инструмент НИКОГДА не возвращает ложный успех. Провал → ошибка
  → Джарвис говорит «не вышло», а не «Готово» (см. error-voice ниже).
- **Автономность/самообучение, не god-objects.** ООП, SRP, модули <150 строк, общие компоненты, DRY.
- **НЕ чат-бот.** Голос — узкий канал; запрет текстового ввода-как-основного (см. project_jarvis_concept).

    1с→60с (сброс после аптайма 60с), watchdog `/healthz` (3 провала подряд → рестарт + АЛЕРТ), алерты:
    **БЕЗ НАСТРОЙКИ** (владелец отказался заводить бота — 2026-07-29): (1) **ГОЛОС САМОГО ДЖАРВИСА** —
    главный канал: супервизор пишет durable-инцидент в `dataDir/incidents.jsonl`, сервер отдаёт ОДНУ
    честную сводку («пока вас не было, я был недоступен и восстанавливался сам — 4 раза, последний
    раз в 4:01») и двигает маркер `incidents-reported.json` (`proactive/incidents.ts`).
    🔴 **Триггер — ПЕРВАЯ РЕПЛИКА ВЛАДЕЛЬЦА, не подключение** (адверс-ревью: ночью клиент из трея
    переподключается САМ через секунду после рестарта → доклад ушёл бы в пустую комнату спящему
    владельцу, маркер бы уехал, и утром он НИЧЕГО не узнал — ровно тот сценарий, ради которого фича
    делалась). `ctx.flushIncidentReport()` (router-ws) зовётся из ВСЕХ каналов первой реплики
    (onUserTurn/onUserTurnStream/dev.text-чат), идемпотентен на сессию, отдаёт ДВЕ копии — голос
    (`speakQueued`, не перебивает) И текст в чат (переживает провал TTS/barge-in/TTL очереди).
    Два гейта потребления (контрольные ревью): **dev-сессия НЕ съедает доклад** (`gateway/dev-session.ts
    isDevSession` — общий с приветствием/сон-циклом: утренний смоук текст-драйвером «съедал» ночной
    инцидент, и владелец не узнавал о нём НИКОГДА) и **занятый владелец** (fullscreen/звонок/locked)
    не потребляет — доклад ждёт следующей реплики, иначе очередь выбросила бы его по TTL при уже
    сдвинутом маркере;
    (2) нативный Windows-toast (PowerShell WinRT — ставить нечего); (3) `msg.exe`; (4) всегда
    `infra/supervisor.log`; троттл 15 мин/тип. **Докладываем не всякий exit:** ручной рестарт владельца
    (документированный dev-цикл) и выключение Windows — НЕ «я падал» (ложный доклад = нарушение
    честности); инцидент пишется, если аптайм <60с (падает на старте) ИЛИ простой ≥`JARVIS_INCIDENT_MIN_DOWN_MS`
    (деф 60с) — владелец реально оставался без Джарвиса; watchdog-рестарт не даёт дубля (`unreportedCrash`).
    Короткий exit ПЕРЕПРОВЕРЯЕТ порт (пауза 1.5с + healthz): отвечает — значит Джарвис жив под ручным
    запуском владельца, наш ребёнок просто проиграл гонку за порт → инцидента нет. Ветка «сервер уже
    отвечает» (watch-only) ЗАКРЫВАЕТ учёт простоя, иначе `downSince` жил бы весь период наблюдения и
    позже дал бы ложное «я был недоступен 12 часов». `recordIncident` в `alert()` идёт ДО троттла —
    троттл гасит попапы, а durable-факт сбоя терять нельзя.
    Telegram-бот (`JARVIS_ALERT_TG_TOKEN`/`JARVIS_ALERT_TG_CHAT`) — ЧИСТО ОПЦИОНАЛЬНОЕ дублирование
    «узнать вне дома»; пусто = штатный режим. ПЕРЕД каждым (ре)стартом —
    проба healthz: живой ручной сервер → режим НАБЛЮДАТЕЛЯ и ВОЗВРАТ в него (не воюем с dev-рестартом
    владельца; EADDRINUSE-грабля); умер → takeover; чужой ЗАВИСШИЙ процесс на порту не убиваем — честный
    алерт. Single-instance PID-лок `infra/supervisor.lock` (живость сверяется по КОМАНДНОЙ СТРОКЕ через
    wmic — ОС переиспользует PID, иначе супервизор молча не стартовал бы; стейл-лок перезаписывается с
    логом); `startServer` под синхронным in-flight латчем (гонка backoff-таймера и watchdog спавнила
    двух детей); fd server.out/err.log закрываются после spawn;
    env-цепочка `JARVIS_ENV_PATH` → `jarvis/.env`. Автозапуск: `infra/register-autostart.ps1` (Task
    Scheduler «JarvisSupervisor» at-logon, `-Remove` снимает; **ASCII-only** — PS 5.1 читает BOM-less .ps1
    как ANSI, кириллица рвёт парс — грабля воспроизвелась живьём). Проверено живьём: краш сервера →
    подъём за 1с; вторая копия супервизора выходит по локу; задача зарегистрирована и запущена.
    Фон аудита: сервер пролежал 2026-07-25→28 три дня БЕЗ единого сигнала.

  LLM-петля → tool-use → (server-side ИЛИ ActionCommand→клиент→актуатор→ActionResult) → ответ →
  verbalize → TTS(Yandex) → speak.chunk → клиент играет.
- **tool→ПК:** LLM эмитит `app_launch{app}` → dispatch → `ActionCommand{kind:app.launch}` →
  Session.sendAction → клиент `actuators/dispatch` → `apps.launchApp` → ActionResult назад.
- **Аренда ввода §20:** GUI-команды (input/app/browser/ui) сериализуются per-session `AsyncMutex`;
  не-GUI (fs/web/код) параллельно (Semaphore(3)).
- **Проактивная речь §9:** `ReminderScheduler` fire → `speakQueued` (тот же канал, что итоги фоновых
  задач) → speak.chunk. Клиент для проактива НЕ дорабатывался.
