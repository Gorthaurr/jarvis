## Приоритет 1 — закрывают наши задокументированные гэпы

### 1.1 Мобильный пульт через бот-мост (⚠️ РЕШЕНИЕ ВЛАДЕЛЬЦА)
Главная рабочая идея Skales: телефон = **не нативное приложение, а мессенджер-бот**. Отдельный
тонкий Node-процесс поллит Telegram (long-polling НАРУЖУ — на ПК не открывается ни один входящий
порт) и форвардит реплики в тот же мозг; результаты/скрины/голос уходят обратно ботом.
- У нас ложится как `infra/jarvis-remote-bot.mjs` рядом с супервизором (PID-лок и бэкофф-паттерн
  готовы) → loopback-эндпоинт `/remote` → `handleUserText` с полноценной сессией; озвучка ответа —
  уже существующий `synthTtsToBase64` (Telegram-voice есть). Пейринг — по коду, привязка
  **per-userId** (не sessionId — грабля cancelUser), durable, троттлинг неверных попыток, лог.
- Бонусом с того же моста: **подтверждения §14 inline-кнопками** (когда владелец не за ПК),
  **аварийный стоп с телефона**, просмотр/отмена §20-задач, доставка скринов **только по явной
  команде** (никогда проактивно).
- ⚠️ 2026-07-29 владелец отказался от TG-бота **для алертов супервизора**. Распространяется ли отказ
  на пульт — вопрос владельцу. Альтернатива — доделать нативный Android (`apps/mobile`) + свой
  E2E-relay, это на порядок дороже. У Skales модель пейринга v12.4.5 хороша целиком: remote-доступ =
  один честный выключатель (деф ВЫКЛ), каждое устройство подтверждается по имени + хвосту ключа,
  удалённое устройство реально отрезается (запрет ре-пейринга до нового QR).
- АНТИ-урок оттуда же: их «execution mandate» («никогда не говори не могу») для удалённого канала —
  прямое нарушение нашего закона честности. Удалённый канал должен УСИЛИВАТЬ confirm, не отключать.

### 1.2 Durable-очередь подтверждений (работает и БЕЗ телефона)
Наш `ctx.confirm` сессионный: владельца нет у ПК → fail-closed отказ, и отложенное действие
(watch-action «когда доставят — напиши Кате») молча протухает (TTL 30 мин).
- Перенять: confirm, который некому показать, **персистится** в dataDir (id, суть действия
  человеческим языком, TTL) → вопрос задаётся при первой реплике владельца (та же точка
  `onOwnerPresent`, что доклад об инцидентах и брифинг) или через будущий пульт → по «да»
  исполняется **ровно сохранённое действие** без повторного планирования (наш же принцип «резюме не
  повторяет вслепую») → протухло = честное «поручение устарело» (уже есть в watch pendingAction —
  механизмы срастутся).
- Мелочь туда же: **pre-check до confirm** — перед вопросом владельцу дёшево проверить, пройдёт ли
  действие последующие гарды (SSRF/денилист/self-guard), чтобы не спрашивать о заведомо блокируемом.

### 1.3 Вкладка «Память» в клиенте (view + delete)
Единственное место, где память Skales лучше нашей — владелец ВИДИТ всё, что о нём накоплено, и
точечно удаляет. У нас память невидима, править можно только голосом (`memory_forget`).
- UI вешается на УЖЕ существующие механизмы (в отличие от Skales, у нас всё готово):
  факты профиля списком + per-item удаление (`removeFactsMatching`); эпизодика с провенансом и
  stale-флагом (удаление = `markStale`, мягко/обратимо); **evicted-архив** («что было вытеснено» —
  витрина честности); кнопка «консолидировать сейчас» (`maybeConsolidate`); счётчики слоёв.
- Паттерн renderer готов: `init<Панель>(jarvis)` как task-panel/billing-panel.
- Первая версия — view+delete, без инлайн-редактирования. Опционально позже: редактируемая
  LLM-сводка «кто владелец» в 3-5 предложений как поле профиля (их `human.content`).

### 1.4 Онбординг и паковка «30 секунд без терминала» (если продуктизация)
У Skales это реально работает, не витрина:
- **Node не бандлится** — серверный процесс запускается самим Electron-бинарём
  (`ELECTRON_RUN_AS_NODE`); мозг собирается esbuild-бандлом (esbuild уже в нашем стеке);
  тяжёлые нативные куски (onnxruntime/DirectML, sherpa-сайдкар, модель e5) — tar.gz в
  extraResources с распаковкой на первом старте и статусом в splash. PGlite-фолбэк уже есть →
  PostgreSQL для чужой установки не нужен. Итог: один NSIS oneClick-exe.
- **Онбординг-мастер**: непропускаемый дисклеймер автономии; ключи Deepgram/Yandex/Anthropic с
  ЖИВОЙ проверкой каждого (реальный вызов, не сохранение вслепую); имя, запись голоса
  (voice-enroll уже есть), выбор степени автономии (маппится на существующие confirm-гейты).
  Ключи — через safeStorage/шифрование как сейчас, НЕ плейнтекст как у них.
- **Авто-апдейт**: electron-updater с generic-провайдером (статический latest.yml + инсталлер;
  sha512-проверка встроена) — у Skales эта половина недоведена, у нас делать до конца. Инвариант
  «апдейт не трогает dataDir» — задокументировать и тестировать.
- **Splash с честной диагностикой старта** (распаковка/миграции/коннект; при фатале — последняя
  строка серверного лога). Ready-детект — по /healthz (он есть), не сниффингом stdout.
- АНТИ-урок: упрощая установку, НЕ переезжать на открытый localhost-веб-API — у Skales мозг
  торчит неаутентифицированным HTTP (Next standalone, судя по env — на 0.0.0.0). Наша модель
  (loopback fail-closed, dev-HTTP за флагом) сохраняется.

### 1.5 Live Capability Registry — «паспорт возможностей» в промпте
У нас знание «что реально доступно прямо сейчас» размазано (каталог §15, detectAutomationTools,
ClientEnv, статусы расширения/сайдкара) — единого снимка модель не видит и узнаёт о мёртвом канале
провалом в рантайме.
- Перенять: derived-снимок `capabilities` с **трёхзначным статусом** — работает / настроено-но-канал-
  мёртв / не настроено (+как включить) — для: расширение подключено? сайдкар жив? календарь-вкладка
  открыта? OBS доступен? ключи на месте?
- Класть МАЛЕНЬКИМ (кап ~300 ток) в НЕкешируемый хвост (рядом с recentTasks — кеш персоны §15 цел).
  Пересборка по событиям (connect/disconnect), не по таймеру. Усиливает закон честности: модель
  ЗАРАНЕЕ говорит «расширение не подключено, сэр — нажмите reload», а не после провала.

### 1.6 Акустический wake-word, обученный на голосе владельца (идея из v12)
Бьёт точно в нашу боль №4 (текстовый wake-матч по STT: «Гарвис/Джервис», зависимость от облачного
STT в простое). У Skales: «скажи имя три раза» → локальное обучение под произношение владельца,
матч на машине, ничего не уходит в облако.
- У нас фундамент есть: sherpa-onnx уже в стеке (speaker-сайдкар, изолированный процесс — конфликт
  onnxruntime решён), sherpa-onnx умеет keyword spotting; UX записи голоса готов (voice-enroll).
  Акустический wake до STT срезал бы и ослышки, и часть STT-трафика в простое.
- Это НЕ копирование Skales (в открытом коде этого нет) — идея из их changelog + свой стек.

### 1.7 Killswitch «полный стоп автономии» + stay-dead латч
У нас есть отмена задач, mute микрофона, супервизор — но нет ОДНОЙ команды «замри вся автономия»
(watch-тики, auto-predictor, проактивные озвучки, отложенные действия) с durable-флагом.
- Критичное отличие от Skales, которое меняет дизайн: наш супервизор ВОСКРЕСИТ убитый сервер через
  1с — killswitch обязан ставить **файл-латч в dataDir, который супервизор уважает** (не рестартует,
  честно алертит «остановлен владельцем»). Снятие — явное действие владельца. Причина — в
  incidents.jsonl → честный доклад при следующем запуске (механизм готов).
- Дёшево; становится важным ДО расширения автономии (watch-action уже шлёт сообщения людям).

## Приоритет 2 — ценные улучшения существующего

### Проактив и видимость
- **Тихие часы** для НЕсрочного проактива: календарное окно «ночью копим до утра» в
  registerSpeaker-гейтах (тот же слой, что isBusy); срочное (инцидент, дедлайн-напоминание)
  проходит всегда. Плюс **per-type переключатели** проактива в UI настроек (сейчас только
  env-флаги, владельцу недоступны).
- **Вечерняя сводка сделанного** (зеркало утреннего брифинга): «сегодня закрыто N задач/наблюдений»
  из реестра §20, окно 16–19ч, раз в сутки, тот же retriable-канал, пусто → молчим.
- **Meeting-prep как вторая ступень** calendar-source: событие С повесткой → ранний сигнал за ~60
  мин (ниже порога озвучки при занятости), обычное напоминание за 20 мин — как сейчас.
- **Таймлайн шагов задачи** в панели §20: история stepLabel+инструментов (копится в Task или
  читается из round-записей metrics.jsonl по taskId), разворачиваемый список в task-panel.ts.
  Добивает жалобу «не показывает, что делает» без единого лишнего токена.
- **Мини-оверлей при скрытом в трей окне** (спорно, решить при реализации): чипы §20 и confirm
  сейчас невидимы, голос — единственный канал. Компактный always-on-top статус (stepLabel + кнопки
  confirm), НИКОГДА поверх fullscreen, обязан подтверждать показ (retriable/onOutcome — иначе
  повторим дыру их Buddy-очереди, где уведомления молча съедались невидимым окном). Маскота не брать.

### Петля и задачи
- **Превентивный чекпойнт на budget-нудже 70%**: сейчас журнал волны C пишется только в терминале
  прерывания — жёсткий kill (краш/OOM/выключение) теряет его. Один дополнительный save-сайт
  (инфраструктура готова), терминал перезаписывает финальной версией.
- **Часовой предохранитель автономных LLM-вызовов**: единый счётчик на ВСЕ автономные вызовы
  (watch-checker, auto-predictor, consolidation, оба reflect) — «не больше N/час», срабатывание =
  WARN + durable-деградация, не тихий дроп. Плюс «K автономных запусков подряд без единой реплики
  владельца → пауза автономных стартов + доклад при первой реплике».
- **Петля generate→validate→retry→Fix для tool_create** (dynamic.ts): валидация (синтакс +
  структурный чек схемы + dry-run) → ошибка скармливается обратно → повтор → сохранение со статусом
  error+lastError → починка по требованию. Плюс декларация requiredSecrets → честное «нет ключа X».
- **Батч-фан-аут не-GUI подзадач** (низко): инструмент «разбей на подзадачи» → несколько петель под
  родительской задачей; только web/fs/code (Semaphore есть), GUI сериализуется арендой как сейчас,
  каждая под SpendGuard. Не для голосовых минутных задач — для будущих больших поручений.

### Безопасность (сверки по их дырам — дёшево и срочно)
- 🔴 **Самоснимаемая песочница — ПРОВЕРИТЬ у нас**: их агент может переписать собственный
  settings.json и снять все гейты. Наш self-guard закрывает .env/node_modules/бинарь — а **mcp.json**
  (confirm-декларации, toolEffect!), profile.json с политиками, будущие файлы confirm-очереди и
  killswitch-латча? Если fs_write может править mcp.json — агент может снять confirm:true с
  MCP-инструмента. Внести поведенческие конфиги в денилист ЗАПИСИ self-guard.
- **Разворачивание URL-шортенеров**: редирект-цепочка сейчас минует browserUrlBlocked (признанная
  дыра «строковый слой не ловит redirect») — разворачивать до конечного URL и гнать ЕГО через гард;
  paste-сервисы помечать в untrusted-обёртке как типовой носитель инъекций.
- **Детектор-телеметрия инъекций**: маркеры («ignore previous instructions»…) в выводе инструментов
  → НЕ блок (ложные срабатывания), а durable `possible_injection{source,marker}` + на этот ход
  поднять строгость (confirm на mutate сразу после заражённого чтения).
- **VirusTotal hash-lookup** скачанного/исполняемого ПЕРЕД «открой/запусти»: SHA-256 + read-only
  сверка; без ключа фича молчит, с ключом — fail-closed до вердикта (у Skales наоборот).
- **Trusted-адресбук отправки** как третий слой §14 (к confirm-once и resend-guard): durable
  per-канальный allowlist получателей; из списка → меньше confirm-усталости, вне списка → confirm
  всегда; **fail-closed** (пустой список = всё через confirm). Гейт в ЕДИНОЙ точке отправки
  (handlers/messaging) — их же баг: гейт обходился их собственным автопилотом.
- Текст fail-closed err у confirm: прямо запрещать модели заявлять исполнение («Do NOT claim this
  action was completed» — их формулировка хороша, перенять слово в слово смысл).

- **Bug-report bundle**: «Джарвис, зафиксируй сбой» → durable-снапшот последних логов/метрик/реплик

- **media_generate** (COLD §15): картинки/видео Replicate BYOK и/или локальный SD на RTX 5080;
  файл в workspace → дальше работают fs_*/telegram_send/office_*. Класса «сделай обложку и отправь»
  у нас нет вовсе.
- **Recency-компонент в эпизодическом recall**: экспоненциальный распад как ТАЙ-БРЕЙКЕР (вес
  ~0.1-0.2), не замена порога честности 0.82.
- **Инкрементальность консолидации**: маркер «что уже просканировано» (mtime>lastScan) — догонять
  пропущенные дни после долгого офлайна, сейчас гейт только календарным днём.
- **Кнопка «повторить заблокированную»** для failed-задач в панели §20 (микро-UX).

### Опт-ин с согласия владельца (НЕ OAuth, но нужен app-пароль)

## Решение владельца (блокирует пункт 1.1)
**Мобильный пульт: Telegram-бот или доделывать Android?**
- (а) TG-бот-мост — 1-2 дня работы, ноль входящих портов, аппрувы+killswitch+статус с телефона
  сразу. Требует завести бота (отказ 2026-07-29 касался алертов супервизора — уточнить, распространяется ли).
- (б) Нативный Android + свой E2E-relay — на порядок дороже, зато без третьей стороны.
- (в) Не делать пульт сейчас. Тогда из 1.1 всё равно стоит взять durable confirm-очередь (1.2) —
  она полезна и локально.

## Анти-уроки (зафиксировать, НЕ повторять)
1. «Execution mandate» / глобальный unrestricted-байпас — против закона честности; удалённый канал
   усиливает confirm, не отключает.
2. Fail-open дефолты (неизвестный инструмент = auto, секрет-не-задан = открыто) — у нас всё
   fail-closed, так держать.
3. Планировщик, СЭМПЛИРУЮЩИЙ паттерн («минута совпала с тиком») вместо расчёта nextRun — их
   ежедневный cron мог не сработать никогда. Наш next-wakeup — правильный.
4. Два параллельных стора задач гарантированно разъезжаются (их cron клал задачи в очередь, которую
   никто не исполнял). Реестр §20 один — так и держать.
5. Авто-переисполнение полусделанных задач после краша = повтор побочных эффектов. Наш «restore →
   честный failed» правильный.
6. Прочитанный из настроек чекбокс безопасности, не доведённый до исполняющего кода — «декларация
   обязана совпадать с поведением» (наш урок D5, у них нарушен повсеместно).
7. Анти-инъекция «просьбой в промпте» без механизма — не работает; работает untrusted-обёртка +
   структурные гейты.
8. Исполнение недоверенного кода «ради метаданных» при импорте навыка — чужой навык = ДАННЫЕ,
   метаданные извлекать статически, первый запуск — после согласия и в отдельном процессе.
9. Молчаливое проглатывание ошибок (.catch(()=>{}) повсюду) — потому их фасады и не всплывали.
   Наши durable-деградации — правильная противоположность.
10. UI-надпись о верификации/автоматике, которой нет («SHA-256 verified» при ручном скачивании) —
    не заявлять фичу до конца цепочки.
