## 0. Что берём, что выкинули

**Каркас — дизайн №1 («припаркованное намерение» + dial-out relay).** Он единственный, у которого фазы 0–1 дают владельцу законченную пользу без единой строки мобильного кода, и он не трогает `bind.ts`.

**Привито из остальных:**
- типизированный `ConfirmOutcome` как дискриминированный union (дизайн №2) — компилятор проводит по всем call-sites;
- четыре различимых исхода `denied / expired / undelivered / deferred` (дизайн №3) — «вы отказали» ≠ «я не смог вас спросить»;
- хранение **точного tool-вызова + хэша тела** и **детерминированное исполнение** вместо LLM-реэнтри (дизайн №3) — обоснование в §2.5;
- SAS-сверка при пейринге (№2/№3), capability-модель устройства (№2), биометрия на approve (№3);
- retriable-контракт волны D на новый канал с самого начала (все три).

**Выкинуто (fatal flaws судей):**
- ❌ обещание «скажете „да" — отправлю» (дизайн №1) — механизма приёма согласия нет, «да» омонимично не хуже «продолжи» у плеера. В фазе 1 голосового приёма НЕТ (§7, решение владельца);
- ❌ тикет по `(tool, targetKey, kind)`, удовлетворяющий **любой** confirm-сайт (дизайн №1) — он нейтрализовал бы ресенд-гард (`messaging.ts:165`). Заменён на позитивный allowlist по structured intent (§2.3);
- ❌ LLM-реэнтри для исполнения отправки (дизайны №1/№2) — противоречие «храним только bodyPreview, а тикет требует совпадения тела» неустранимо (§2.5);
- ❌ `XChaCha20 через Node createCipheriv` и `Noise IK на эфемерном ключе из QR` — обе спецификации внутренне несогласованы (§4.2);
- ❌ FCM как обязательная зависимость — требует Firebase-регистрации, которую владелец отвергал дважды (§7);
- ❌ очередь произвольных отложенных **команд** — новый класс «протухшее действие». Откладываются только подтверждения (решение уже принято владельцем), команды — либо исполняются сейчас, либо честный отказ.

## 1. Инварианты и как каждый соблюдён

| Инвариант | Механизм |
|---|---|
| 1. Закон честности | Парковка возвращает `ok` **без** `ToolResult.sent` → `anyMutateSucceeded` не взводится (`agent/index.ts:2713`), masked-failure-гард жив, терминал не скажет «Готово». Обещание «ждёт вас» гейтится **фактом записи на диск** (зеркало `canResume` волны C). Истечение и вытеснение **проговариваются**, не исчезают. |
| 2. FAIL-CLOSED, портов на ПК ноль | `gateway/bind.ts:resolveBindHost` не трогается ни строкой. `JARVIS_ALLOW_REMOTE`/`JARVIS_AUTH_STRICT` остаются выключены. ПК **набирает наружу** (`relay-link.ts` — WS-клиент). Единственный слушающий процесс во всей схеме — relay на VPS, у которого нет ни ключей, ни доступа к ПК. |
| 3. §14 усиливается, не отключается | Парковка не выдаёт вечное согласие (§2.8). Парковаться может **только** первичный send-гейт; ресенд/similar-гейт непарковочный по конструкции. `irreversible`/`order` не паркуются и с телефона не подтверждаются никогда. Одобрение на телефоне требует биометрии. |
| 4. Retriable-контракт | Уведомление о припаркованном идёт `speakQueued(text, false, {retriable:true, onOutcome})`; durable-пометка «владельцу сказали» ставится **только** по `onOutcome(true)`. Доставка на устройство помечается только по E2E-ACK устройства, не по факту записи в relay. |
| 5. Один стор задач; только позитивные allowlist | `approvals.json` — **не** второй реестр задач: в нём нет lifecycle задачи, задача терминируется честно, а исполнение создаёт настоящую §20-Task. Парковка включается **явным** structured intent на call-site (allowlist), а не денилистом по `kind`. Приём «да» голосом — позитивный allowlist форм, если владелец его закажет. |
| 6. dev-сессия не потребляет | `registerApprovalChannel` и `registerRemoteEndpoint` — под тем же `if (!devSession)`, что `reminders.registerSpeaker` / `watch.registerRunner` / `ambient.registerSpeaker` (`router-ws.ts:643,659,673,688`). Это **6-й и 7-й** register* в проекте с этим требованием — регресс-тест обязателен. |

## 2. Durable confirm: «парковка намерения»

### 2.1. Корень (проверено по коду)

`ctx.confirm` (`agent/index.ts:1403-1406`) — это `await session.requestConfirm({... expiresAt: Date.now()+60_000})` **внутри** tool-цикла петли, у которой потолок `JARVIS_TASK_MAX_MS` = 4 мин (`index.ts:1438-1442`). Ждать часами физически нельзя.

Хуже: `Session.requestConfirm` (`session.ts:189`) **не имеет fail-fast**, который есть у `sendAction` строкой выше (`session.ts:153-156`). При закрытом сокете `send()` только пишет warn, а таймер всё равно отсчитывает 60 с и резолвит `approved:false` — **25 % потолка задачи сожжено, и владельцу говорят «вы не подтвердили» про вопрос, которого он не видел.** Это существующий дефект честности, а не гипотеза.

И `teardown()` (`session.ts:229`) резолвит все висящие confirm как `{requestId: "", approved: false}` — настоящий requestId теряется.

**Решение: петля никогда не ждёт дольше короткого окна. Откладывается САМО НАМЕРЕНИЕ** — прямая копия уже отревьюенного `watch.pendingAction` (`proactive/watch/service.ts:424-474`).

### 2.2. Контракт `ConfirmOutcome` (типовая миграция)

```ts
// packages/protocol/src/messages.ts — АДДИТИВНО
export type ConfirmOutcomeKind = "approved" | "denied" | "expired" | "undelivered" | "deferred";
```

```ts
// brain/tools/dispatch.ts
export interface ConfirmIntent {                    // ← НОВОЕ: структурное намерение
  tool: "telegram_send" | "telegram_send_voice" | "message_send";
  channel: string;                                   // telegram | vk | …
  recipient: string;                                 // как назвал владелец
  peerId?: string;                                   // точная идентичность (peerIdentityKeys)
  body: string;                                      // ПОЛНОЕ тело, не превью
  input: Record<string, unknown>;                    // точные аргументы вызова
  parkable: true;                                    // явное разрешение парковки
}

confirm?: (
  summary: string,
  kind?: "send" | "order" | "irreversible",
  intent?: ConfirmIntent,                            // ← третий, необязательный
) => Promise<ConfirmOutcome>;

export interface ConfirmOutcome {
  outcome: ConfirmOutcomeKind;
  approved: boolean;      // производное: outcome === "approved" — НЕ оставлять единственным полем
  revision?: string;
  approvalId?: string;    // при outcome === "deferred"
}
```

Менять возвращаемый тип **обязательно** (урок контроля-8 волны D: «тип канала был `=> void`, и компилятор не мог указать на пропуск»). Затронутые call-sites — 10 прямых + 2 обёртки:

`dispatch.ts:362` (MCP), `dispatch.ts:428` (fs/system/app), `handlers/code.ts:33`, `handlers/skills.ts:35`, `handlers/watch.ts:111`, `handlers/messaging.ts:32` (`confirmSendOnce`), `:165` (ресенд), `:255`, `:289/313/323/339`, `:373/381`; обёртки `messaging/outbound.ts:28,83` и `orders/orders.ts:19,58`.

**Правило миграции:** каждый call-site обязан явно решить, как звучит `deferred` и `undelivered`. Не оставлять `approved: boolean` единственным полем — иначе по инерции всё деградирует в deny.

### 2.3. Что паркуется — позитивный allowlist на call-site

Паркуется **ровно один** confirm-сайт: первичный гейт отправки (`confirmSendOnce`, `messaging.ts:32`) для `telegram_send` / `telegram_send_voice` / `message_send`. Он единственный передаёт `intent.parkable`.

**Не паркуется никогда:**
- **ресенд/similar-гейт** (`messaging.ts:165`) — повтор/вдогонку человеку необратим, и одобрять его в отсутствие владельца нельзя. Он `intent` не передаёт → при мёртвом канале прежний честный отказ. *Это и есть закрытие fatal flaw №1 у дизайна №1: тикет физически не может удовлетворить этот сайт, потому что сайт не парковочный.*
- `irreversible` (fs_delete, system_power, app_close{force}, code-guard, skill-guard, MCP-confirm, `watch_create{action}`) — отложенное на час удаление/выключение = исполнение в потерянном контексте;
- `order` (деньги) — политика проекта.

Для них `undelivered` → прежний `err(...)`, fail-closed, без единого обещания.

### 2.4. Стор и запись

`apps/server/src/gateway/approvals/store.ts` — зеркало `brain/agent/checkpoint-store.ts` (атомарно tmp→rename, восстановление с отсевом протухших, `peek` отдаёт **копию** — урок дефекта #23 волны C про алиасинг).

```ts
interface PendingApproval {
  id: string; userId: string;
  taskId?: string;                      // связь с §20-задачей, породившей запрос
  createdAt: number; expiresAt: number;
  state: "parked" | "approved_pending_exec" | "executing" | "done" | "denied" | "expired" | "frozen";
  kind: "send";
  tool: ConfirmIntent["tool"];
  input: Record<string, unknown>;       // ТОЧНЫЕ аргументы (исполняем ровно их)
  channel: string; recipient: string; peerId?: string;
  summary: string;                      // ровно то, что видел бы владелец в модалке
  fingerprint: string;                  // sha256(tool|channel|peerIdentityKey|normalizeSendBody(body))
  bodySha256: string;                   // подпись владельца привязана к КОНКРЕТНОМУ телу
  delivery: Array<{ endpointId: string; kind: "desktop"|"remote"; deliveredAt?: number; ackAt?: number }>;
  offeredAt?: number;                   // владельцу РЕАЛЬНО сказали (отдельно от факта записи)
  answer?: { approved: boolean; at: number; via: "desktop"|"remote"; deviceId?: string; biometric?: boolean };
}
```

- Файл: `data/approvals.json`. Кап `JARVIS_APPROVAL_MAX` (деф 20 на пользователя). **Вытеснение pending запрещено**: переполнение → новая парковка отклоняется с честным «очередь подтверждений переполнена, не отправил» (нельзя молча выбросить обязательство ради дубля — класс волны D).
- **Дедуп по `fingerprint`** на создании: повторная парковка того же намерения возвращает **тот же** `approvalId`, а не вторую запись. Закрывает fatal flaw №4 судьи дизайна №2 (модель повторит вызов в тех же 4 минутах).
- TTL `JARVIS_APPROVAL_TTL_MS`, деф 2 ч, кламп [5 мин, 24 ч] (значение — решение владельца, §7).
- `fingerprint` считается **не из summary**: в summary вшито изменчивое `agoOf` (`messaging.ts:80-82`) и тело обрезано `slice(0,160)` (шесть мест) — совпадение развалилось бы само, а два разных длинных письма одному человеку дали бы **один** отпечаток.
- `approvals.json` → `POLICY_BASENAMES` в `apps/client/main/actuators/self-guard.ts:96` (запись `approved:true` через `fs_write` = автономная отправка от имени владельца; тот же класс, что `watches.json` с его `pendingAction`). Туда же `remote-devices.json`. `relay-identity.key` уже покрыт регексом `/\.(pem|key|…)$/` в `isSecretPathNorm` — проверить тестом, не добавлять дубль.

### 2.5. Исполнение по «да» — детерминированное, БЕЗ LLM

**Решение: исполняем СОХРАНЁННЫЙ вызов той же функцией-хендлером, под тем же `sendLock(userId)`, с полным повторным прогоном всех §14-гардов. LLM-реэнтри через `handleUserText` для этого — ОТКЛОНЁН.**

Почему не реэнтри (это главный архитектурный выбор документа):

1. Владелец видел на экране **конкретный текст**. Новая петля напишет «примерно то же», и его подпись окажется под другим действием.
2. Дизайн №2 споткнулся ровно здесь: тикет требует совпадения нормализованного тела, а хранится только превью → отпечаток **систематически не совпадёт** → одобрение выродится в «спросил снова» по кругу. Хранить полное тело и при этом просить модель его воспроизвести — бессмысленный крюк.
3. Парковочный набор **закрыт и мал** (три инструмента отправки), поэтому детерминированный путь полностью аудируем — в отличие от общего реэнтри.
4. Нет LLM-вызова → нет расхода, нет проблемы «SpendGuard в обход», нет риска, что модель на реэнтри решит сделать что-то ещё.

Возражение «сохранится ли §20-видимость и honesty-гарды» снимается так: исполнение **создаёт настоящую §20-Task** («выполняю отложенную отправку»), чип виден, терминал честный, метрика пишется, `ToolResult.sent` решает исход — тот же единственный честный признак, что и в петле.

Порядок исполнения (`approvals/service.ts`):

```
resolve(approvalId, approved, via, deviceId)
  → CAS state: parked → approved_pending_exec   (единственный арбитр гонки «ответили с ПК и с телефона»)
  → persist на диск
  → живая сессия владельца есть?  нет → ждём (flushApprovals при registerApprovalChannel + свой таймер дренажа)
  → autonomyFreeze().isFrozen()?  да → state=frozen, честный ответ на телефон «принял, но автономия остановлена»
  → TTL истёк?                    да → state=expired, НЕ исполняем, честно проговариваем
  → state=executing, persist ДО вызова           (at-most-once — копия flushPendingActions:463-465)
  → tasks.start(«отложенная отправка …»)
  → sendLock(userId).acquire()
      → строим ToolContext: { session: живая сессия, userId, origin:"user",
                              confirm: ticketConfirm(fingerprint)  ← одноразовый, см. ниже
                              …остальные deps }
      → telegramSend(ctx, approval.input)        ← ТА ЖЕ функция, что в петле
        внутри неё заново: sentKeys, ResendGuard, CadenceGuard, резолв адресата, ctx.confirm
  → r.sent === true ? tasks.finish(ok) : tasks.fail(честная причина)
  → state=done, persist; уведомление владельцу/устройству по факту
```

`ticketConfirm(fingerprint)` — одноразовое замыкание: возвращает `{outcome:"approved"}` **только** если пришедший `intent` даёт тот же `fingerprint`, и **только один раз**; иначе — обычный путь (спросить), т.е. fail-closed. Так одобрение не «отмывается» в мандат на соседний вызов внутри того же исполнения.

Если гарды заново срезали отправку (ResendGuard увидел свежую ручную отправку тому же человеку) — это **честный неуспех**, а не тихий пропуск: владельцу говорится «не отправил: вы уже написали ему сами».

### 2.6. Честность в момент парковки — точные формулировки

```ts
// messaging.ts, ветка confirmSendOnce
if (gate.outcome === "deferred")
  return ok(
    `Не отправил «${to}» — жду вашего подтверждения. Запрос сохранён (№${gate.approvalId}), ` +
    `действителен до ${hhmm(expiresAt)}. Повторно этот вызов НЕ делай и НЕ пытайся отправить ` +
    `обходным путём (набор текста в мессенджере через браузер/клавиатуру) — это тот же гейт.`
  );   // ⚠️ БЕЗ sent:true
if (gate.outcome === "undelivered")
  return ok(`Не отправил «${to}» — не смог задать вам вопрос: канал подтверждения недоступен.`);
if (gate.outcome === "denied")
  return ok(`Не отправил — вы не подтвердили отправку «${to}».`);   // как сегодня
```

- `ToolResult` получает новое поле `deferred?: { approvalId: string }` (аддитивно).
- Терминал хода: `taskOk = false`. Иначе самообучение сохранит навык из траектории, которая ничего не сделала (урок фикса 37 волны C), и метрики зафиксируют ложный успех.
- Голос владельцу: «Подготовил сообщение Кате, отправлю после вашего подтверждения». **Никогда** «Готово» / «Отправил».
- Если стор не принял запись (диск, кап, выключено `JARVIS_APPROVAL_QUEUE=0`) → `outcome:"undelivered"`, **никакого обещания** «ждёт вас».

### 2.7. Связка с существующими волнами — обязательные правки

Это места, где новая фича сталкивается с уже написанным. Пропуск любого = возврат закрытого класса дефектов.

**(а) Волна C, журнал чекпойнта — конкретный путь двойной отправки.** `saveCheckpoint("hardKill")` стоит на 70 %-нудже (волна E, E4), а `outcomeMark` (`checkpoint.ts:255`) для несостоявшейся отправки пишет **«ОТПРАВКА НЕ ПОДТВЕРЖДЕНА — сверь, при необходимости отправь»**. Сценарий: парковка → задача упёрлась в бюджет → журнал → «доделай» → модель отправляет руками → через час владелец одобряет припаркованное → **вторая отправка**. Все защиты к тому моменту мертвы (`sentKeys` 10 мин, ResendGuard 2 мин).

Фикс — симметрично `confirmedSends`:
```ts
// agent/index.ts, рядом с :2716
if (r.deferred) parkedSends.set(tu.id, r.deferred.approvalId);
// checkpoint.ts outcomeMark:
if (parkedSends?.has(e.id))
  return "ОТПРАВКА ОТЛОЖЕНА и стоит в очереди подтверждений — НЕ отправляй повторно";
```
`buildResumeDigest` принимает `parkedSends` рядом с `confirmedSends` (все 5 call-sites: `:1544, :2004, :2772, :3166` и терминалы).

**(б) Волна D, retriable.** Уведомление «есть N подтверждений» — **несрочное**, `retriable:true`, `onOutcome` откатывает `offeredAt`. Свой таймер дренажа с полом 30 с. Гейт «занят владелец» и тихие часы (E5) применяются: это не будильник.

**(в) Волна E, killswitch.** `autonomyFreeze()` гейтит **исполнение** одобренного (не саму рассылку вопросов — вопрос владельцу это не автономия). Гейт обязан **перевзводить таймер дренажа**, а не делать голый `return` (HIGH контроля-1 волны E на `watch.tickNow`), иначе «включи автономию» даст бодрый ack при молчащей очереди. `unfreeze` дополнительно пинает `flushApprovals`.

**(г) dev-гейт.** `registerApprovalChannel` — под `if (!devSession)`. Иначе утренний прогон текст-драйвера потребит очередь, durable-пометит доставленной и **исполнит** отправку живому человеку с «подтверждением» от тестового скрипта. Это буквально сценарий, который контроль-5 волны D нашёл у `watch.registerRunner`.

**(д) `session.ts` — два самостоятельных фикса (ценны без пульта):**
- `requestConfirm`: fail-fast при `this.socket.readyState !== WS_OPEN` **и** отсутствии зеркального канала → мгновенный `undelivered`;
- `teardown`: резолвить настоящим `requestId` и `outcome:"undelivered"`, а не `{requestId:""}`.

### 2.8. Согласие (`consent.json`) — критично, ни один дизайн не заметил

`confirmSendOnce` (`messaging.ts:33`) на любом `approved` зовёт `approveSend`, а `consent.ts` пишет согласие по `(userId, channel, recipient)` **навсегда** (лог буквально: «согласие на отправку сохранено (навсегда)»). Ресенд-ветка (`:169`) делает то же самое.

Значит **одно «да» с телефона сняло бы §14-гейт для этого адресата насовсем**, для всех будущих текстов, включая те, что модель напишет сама. Украденный телефон получает не одну отправку, а постоянный канал. Это прямое нарушение инварианта 3.

**Решение (дефолт):**
- одобрение, пришедшее **с remote-устройства**, `approveSend` **НЕ вызывает** — оно одобряет ровно это тело (`bodySha256`);
- одобрение с ПК сохраняет сегодняшнее поведение (регресса нет);
- в `consent.json` при записи фиксируется `via` — для аудита.

Альтернатива (TTL у согласия, «переспрашивать раз в N дней») — **решение владельца**, §7.

## 3. Relay и удалённый канал

### 3.1. Топология

```
[Android-пульт] --wss(dial-out)--> [jarvis-relay, VPS 46.253.132.247] <--wss(dial-out)-- [ПК: apps/server]
```

Оба конца **набирают наружу**. На ПК не появляется ни одного слушающего сокета, роутер/NAT/файрвол не конфигурируются, DDNS не нужен, входящий скан ПК ничего не находит. Вектор «сосед в Wi-Fi самопровижнит userId и гонит ActionCommand → RCE», ради которого писался fail-closed в `bind.ts`, не открывается.

Relay — **слепой почтальон**: сопоставляет два конца по `linkId`, форвардит непрозрачные конверты, держит bounded-очередь на время офлайна. Не парсит содержимое, не хранит ключей, не является авторитетом. Компрометация VPS = метаданные + DoS, **не** команды на ПК.

### 3.2. Relay-сервис

`apps/relay/` — **standalone-пакет вне pnpm-workspace** (`pnpm-workspace.yaml` = `packages/*`, `apps/server`, `apps/client`; прецедент — `apps/extension`). Осознанно: relay **не должен** импортировать ни строки кода Джарвиса, иначе рано или поздно начнёт понимать содержимое.

- Node 20 + `ws`, ~300–400 строк, без БД (файловая очередь).
- Эндпоинты `wss /link` (ПК) и `wss /device` (телефон); авторизация подключения — `linkId` + Ed25519 challenge-response по зарегистрированному публичному ключу. Это анти-чужак, **не** защита содержимого.
- Очередь: per (linkId, direction), кап по числу и байтам, at-least-once с ACK по `messageId`. TTL **разный по типу**: уведомления о подтверждениях 24 ч, **команды 15 мин** (протухшая команда не должна исполниться через час).
- `max frame 256 KB`, rate-limit на link, отказ на неизвестный linkId.
- systemd: `User=jarvis-relay`, `NoNewPrivileges=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `MemoryMax=256M`, `Restart=always`. Caddy/nginx впереди, `ufw` открыт только 443.
- Логи — без plaintext (его нет), только метаданные.

### 3.3. `relay-link.ts` на ПК

`apps/server/src/remote/relay-link.ts` — зеркало отлаженного `apps/client/main/transport/index.ts`, но с интернет-параметрами:

- backoff 1 с → 60 с с джиттером (у локального клиента кап 5 с — он занижен под loopback, здесь это был бы шторм);
- прикладной heartbeat 20 с, 2 промаха → terminate → reconnect; `unref` на таймерах; single-flight латч на connect;
- **исходящий outbox** at-least-once (копия `transport.outbox`) с капом и TTL;
- **входящий дедуп** по `(deviceId, seq)` — at-least-once relay не превращается в двойное исполнение;
- поднимается в `gateway.listen()` **только** при непустом `JARVIS_RELAY_URL` (пусто = фичи нет, дефолт), dispose в `close()`;
- **boot-лог честно объявляет**: «пульт включён, исходящее соединение на `<host>`». Новый канал наружу не должен появляться тихо.

**При обрыве:** истина всегда на ПК. Телефон без ACK от ПК показывает «ПК недоступен — команда НЕ доставлена», а не «отправлено». ПК без relay работает ровно как сегодня; припаркованные подтверждения ждут владельца у машины. Живость ПК на телефоне показывается **по подписанному ПК хартбиту**, а не по слову relay.

### 3.4. Вход команд (`remote/ingress.ts`) — и починка канала ответа

Команда с пульта **не исполняется в relay-link'е**. Она заходит в `handleUserText` через runner, зарегистрированный в `router-ws` (паттерн `watch.registerRunner:673`, под тем же dev-гейтом).

Гейты по порядку: устройство доверено и не отозвано → `capability.command` → killswitch (реплика **владельца** проходит, как напоминания; отложенная автономия — нет) → rate-limit `JARVIS_REMOTE_CMD_PER_HOUR` (деф 60, скользящее окно как `autonomy/throttle.ts`) → `meta = { origin: "remote", viaWake: false }`.

`viaWake:false` обязателен: слепой авто-реплей макроса на удалённой команде запрещён (прецедент `replay-gate`).

**🔴 Починка канала ответа (fatal flaw, найденный судьёй дизайна №1).** `agentDeps.speakResult` и `taskAccepted` — синглтоны сессии, захваченные в замыкании `makeSessionContext` (`router-ws.ts:~630`). Команда с телефона, промоутнутая в §20-задачу, ушла бы **голосом в пустую комнату**, а на телефон не пришло бы ничего.

Фикс дешёвый и обязательный — **per-turn клон deps**:
```ts
// remote/ingress.ts
const remoteDeps: AgentDeps = {
  ...agentDeps,
  speakResult: (reply) => {
    remoteEndpoint.send({ type: "chat", text: reply.voice, display: reply.display });
    if (speakOnDesktop) agentDeps.speakResult?.(reply);   // деф false: владельца дома нет
  },
  taskAccepted: () => remoteEndpoint.send({ type: "ack" }),
};
void handleUserText(session, text, remoteDeps, undefined, { origin: "remote", viaWake: false })
  .then((reply) => { if (reply.voice.trim()) remoteDeps.speakResult?.(reply); });
```
`AgentDeps` — обычный объект, клон безопасен. Регресс-тест: «фоновая задача, поднятая remote-командой, отдаёт итог в remote-endpoint и не озвучивает его на ПК».

**Исполнителем остаётся живая сессия Electron.** `telegram_send` идёт через `ctx.session.sendAction` в Electron (`messaging.ts:186`), актуаторы живут там же. Значит:
- Electron-клиент жив → команда исполняется в его сессии, ответ уходит на телефон;
- Electron закрыт → **честный отказ** «ПК недоступен: клиент не запущен», команда **не копится**. Осознанная асимметрия с подтверждениями (там решение уже принято владельцем, откладывание — суть фичи).

**`onOwnerPresent` из remote-канала НЕ вызывается.** Иначе доклад об инцидентах и сводка дня уедут в телефон, durable-маркеры сдвинутся, и владелец у ПК не узнает ничего никогда — тот самый класс, который в проекте ловили трижды (dev-сессии, ночной reconnect из трея). Решение записать **в `jarvis/CLAUDE.md` явно**, с регресс-тестом; в коде молча оставлять нельзя.

## 4. Пейринг, крипто, отзыв

### 4.1. Пейринг — локальный, с двусторонней сверкой

1. ПК: Настройки → «Пульт» → «Добавить устройство». Генерируются **статический** X25519 ПК (если ещё нет) и одноразовый `linkId`; у relay берётся пейринг-слот, TTL 3 мин, single-use.
2. QR **на экране ПК**: `{relayUrl, linkId, pcStaticX25519Pub, pcEd25519Pub, pairingToken, expiresAt}`. Канал офлайн — relay в этом шаге ключей не видит.
3. Телефон сканирует, генерирует свои Ed25519 + X25519 в Android Keystore (StrongBox при наличии, `setUserAuthenticationRequired(true)`), подключается к relay, шлёт свои публичные ключи.
4. **SAS-сверка**: обе стороны выводят 6-значный код из `BLAKE2s(pcPub ‖ devPub ‖ linkId)` и показывают на своих экранах. Владелец сверяет глазами и подтверждает **штатной §14-модалкой на ПК** (`confirm-dialog.ts`, `kind:"irreversible"`). Ключ телефона приходит **через relay**, поэтому без SAS враждебный relay встал бы посередине. Не совпало → пейринг рвётся, `linkId` сжигается.
5. `data/remote-devices.json` (атомарно): `{deviceId, name, ed25519Pub, x25519Pub, epoch, pairedAt, lastSeenAt, lastSeq, capabilities, enabled}`. Секрет ПК — `data/remote/relay-identity.key`, зашифрован существующим `db/crypto.ts` (AES-256-GCM под `CREDENTIALS_MASTER_KEY`).
6. **Битый/нечитаемый `remote-devices.json` = нет доверенных устройств** (fail-closed, зеркало `autonomy-freeze.ts`: битый файл = латч стоит).
7. **Capabilities, дефолт минимальный:** `approve:true`, `status:true`, `command:false`. Скоуп `command` включается владельцем отдельным тумблером на ПК. Скоупа для `irreversible`/`order` **не существует как конструкции** — телефон такой запрос видит, но кнопка недоступна с честной подписью «требует подтверждения за компьютером». Пульт не может породить новый пульт и не может менять свои скоупы.

### 4.2. Крипто — и почему именно так

Три предложенных дизайна дали три несогласованные спецификации; фиксирую одну.

**Примитив: XChaCha20-Poly1305 из libsodium с 24-байтным СЛУЧАЙНЫМ nonce.**
- Node: `sodium-native` (или `libsodium-wrappers`); Android: `lazysodium-android`.
- ❌ **Не** `createCipheriv` — в OpenSSL/Node нет XChaCha20 (24-байтный nonce); «XChaCha через Node нативно» из дизайна №2 — ошибка.
- ❌ **Не** персистентный счётчик-nonce при статичном долгоживущем ключе (дизайн №1): краш или откат файла счётчика между отправкой и флашем = **повтор nonce**, а это компрометация ключа аутентификации, а не «шум». 24 случайных байта убирают весь класс.
- ❌ **Не** ручная Noise-стейт-машина на двух языках (дизайн №3): её спецификация сама себе противоречила (IK требует знания статического ключа ответчика, а QR нёс «эфемерный»), и писать её дважды — источник дефектов там, где их цена максимальна.

**Ключи направления:** `shared = X25519(pcStatic, devStatic)`; `HKDF-SHA256(shared, salt = linkId ‖ epoch, info = "jarvis-remote-v1|pc->device")` и обратный. Компрометация разбора одного направления не даёт подделать другое. Ротация — `epoch++` (репейринг или команда владельца), напоминание раз в 90 дней через существующие reminders.

**AAD** = `{linkId, deviceId, direction, seq, type}` — relay не может ни переклеить кадр на другое устройство, ни подменить тип.

**Анти-реплей — на прикладном уровне, не на nonce:** монотонный `seq` внутри plaintext, приёмник держит `lastSeq` + битовую маску 1024 (durable, в `remote-devices.json`), окно свежести `|ts − now| ≤ 90 с`. **Второй рубеж, независимый от крипто:** `approvalId` одноразов и `state` durable — даже успешно переигранный кадр «approve» второй отправки не даст.

**TLS** (Let's Encrypt или самоподписанный с пиннингом отпечатка) — внешний слой против сетевого наблюдателя. Он **не** граница доверия: relay терминирует TLS и всё равно ничего не понимает.

**Что relay видит:** `linkId`, `deviceId`, направление, размер, время, seq. **Не видит:** тексты команд, тела сообщений, имена адресатов, summary подтверждений, транскрипты.

### 4.3. Отзыв — три независимых рубежа, каждый работает в одиночку

1. **Авторитетный (ПК):** Настройки → «Пульт» → «Отозвать». Строка удаляется из `remote-devices.json` → ключ уничтожен → кадры устройства физически не расшифровываются. Работает, даже если relay скомпрометирован или врёт. Идемпотентно, переживает рестарт.
2. **Быстрый (relay):** `DELETE /pair/<deviceId>` подписанным ПК-запросом (или руками владельца по SSH) — сокет рвётся мгновенно, даже когда ПК выключен («телефон украли, я в отпуске»).
3. **Тотальный:** пустой `JARVIS_RELAY_URL` / тумблер «Пульт выключен» → канал не поднимается вовсе.

Плюс: **голосом** — «отвяжи телефон» / «отвяжи все устройства» через anchored-allowlist в `task-control.ts` **перед** классификатором задач (тем же приёмом, что killswitch волны E); ack ветвится по **реальному durable-исходу** (не удалось записать — говорим, что отзыв действует до перезапуска). **Самоотзыв с телефона разрешён** (снижение привилегий безопасно); обратной операции с телефона нет никогда. **Автоотзыв** по бездействию `JARVIS_DEVICE_IDLE_DAYS` (деф 90) → `enabled:false` + честное уведомление, не тихое удаление. **Попытка подключения отозванного устройства** → durable-аудит + одно проактивное уведомление (троттл 1 ч).

**Побочные эффекты, которые нельзя проглотить:** припаркованные подтверждения, ждавшие отозванного устройства, **не исчезают** — переадресуются на ПК; одобрение «в полёте» от отозванного устройства отвергается fail-closed с честным «пришло одобрение от отозванного устройства — не выполнил».

**Killswitch «полный стоп» устройства НЕ отвязывает** (это канал владельца, как напоминания), но замораживает исполнение одобренного — и ack проговаривает это явно, чтобы владелец не думал, что его «да» уже сработало.

### 4.4. Аудит

`data/remote/audit.jsonl`: кто, с какого устройства, когда, что одобрил/скомандовал, чем кончилось (`bodySha256`, `via`, `seq`, `biometric`). Удалённый канал без журнала непроверяем и недоказуем при разборе «я этого не подтверждал».

## 5. Протокол — строго аддитивно

`isProtocolCompatible` — **строгое равенство** (`packages/protocol/src/index.ts:49-51`). Любой bump `PROTOCOL_VERSION` мгновенно кладёт связь с существующим Electron-клиентом. **Версию не трогаем.**

// messages.ts — только опциональные поля и новые MessageType

ConfirmResult   += outcome?: ConfirmOutcomeKind, via?: "desktop"|"remote", deviceId?

**Итого 28–44 дня работы + 11–17 дней ревью.** Диапазон Ф4 самый широкий: рабочего Android-тулчейна в среде нет (`apps/mobile` — 3 Kotlin-файла чужой фичи: `ApiClient`, `GeofenceManager`, `PushService`), нет эмулятора, не заложены подпись и сайдлоад APK — это зависит от машины владельца (§7).

**Точка разреза, если проект придётся остановить:** после Ф1. Ф0+Ф1 — это чистый выигрыш честности и реально работающая отложенная отправка на одном ПК, без сети, без крипто, без Android.

**Почему запрос владельца («команды со смартфона») не в первой фазе:** для него физически нужны relay + E2E + пейринг + Android. Ф3 с заглушкой-телефоном — первый момент, когда команда действительно долетает до ПК и исполняется; Ф4 лишь заменяет заглушку на телефон. Ускорить можно только одним способом — см. решение №9 в §7.

## 7. Что решает ВЛАДЕЛЕЦ (не мы)

Ни одно из этих решений нельзя принять за него: они либо меняют профиль риска, либо требуют его регистраций/железа, либо касаются денег.

1. **Принятие корневого риска.** Пульт = удалённое управление Windows-машиной с `code_run` и полными правами. **Украденный разблокированный телефон ≈ компрометация ПК.** Смягчения (биометрия, скоупы, отсутствие irreversible/order, быстрый отзыв) сужают, но не закрывают класс. Строить или нет — его решение.
2. **Новый исходящий канал с ПК.** Даже при нуле входящих портов это труба наружу, по которой ходят summary подтверждений (имена адресатов, куски сообщений). Осознанное согласие нужно до Ф3.
3. **TLS для relay: домен или пиннинг.** Let's Encrypt **не выдаёт** сертификаты на голый IP `46.253.132.247`. Либо купить/направить домен, либо самоподписанный сертификат с пиннингом отпечатка в обоих клиентах (рекомендую — оба конца наши, зависимости от регистратора нет).
4. **FCM/Firebase — да или нет.** Пуш требует Firebase-проекта, то есть регистрации, которую владелец отвергал дважды. **Дефолт документа: без FCM** — foreground-service с постоянным WSS + исключение из battery optimization. Цена: доставка уведомлений в глубоком Doze менее надёжна (компенсируется тем, что ПК-канал первичен, а недоставленное честно объявляется). Если FCM всё-таки нужен — пуш будет **contentless** (`{linkId, seq}`, ноль полезной нагрузки).
5. **Согласие после удалённого «да».** Рекомендация: remote-одобрение **не** пишет вечный `consent`. Альтернативы: (а) как сейчас — навсегда для всех каналов; (б) TTL у согласия (переспрашивать раз в N дней) — это изменит поведение и на ПК тоже.
6. **TTL припаркованного подтверждения.** Рекомендация 2 ч. Больше = выше риск исполнения в изменившемся мире; меньше = чаще «истекло, не отправил».
7. **Голосовой приём «да».** Строим ли окно предложения по образцу `RESUME_OFFER_WORD` (однозначное слово, позитивный allowlist форм, окно приёма)? **Дефолт: не строим** — одобрение только карточкой (ПК/телефон). Это ~2–3 дня + отдельный раунд ревью, потому что «да» омонимично.
8. **Физический ввод по команде с телефона, когда владелец за ПК.** Мышь/клавиатура могут дёрнуться посреди его работы или игры. Гейтить по presence (спрашивать/отказывать, если пользователь активен) или исполнять безусловно как его собственную команду?
9. **Можно ли ускорить Ф4.** Варианты: (а) ждать нативный Android (его выбор, 8–14 дней); (б) промежуточный web-клиент на relay под TLS (быстрее, но ключ в браузере — слабее, и это отдельная поверхность); (в) сузить MVP до «только подтверждения», без команд. Рекомендую (в) → (а).
10. **Android-окружение.** Установлены ли Android Studio/JDK/SDK на его машине, есть ли устройство для сайдлоада, как подписываем APK. Без этого Ф4 не стартует.
11. **Relay на общем VPS или выделенном пользователе.** На `46.253.132.247` уже что-то живёт? Нужен ли отдельный systemd-пользователь и изоляция.
12. **Бюджет адверс-ревью.** Правило владельца — до нуля находок. По истории это 4–7 проходов на волну; в оценках это отдельные 11–17 дней. Подтвердить.

## 9. Что мы сознательно НЕ делаем

- **Не открываем портов на ПК и не трогаем `bind.ts`.** Ни строки.
- **Не бампаем `PROTOCOL_VERSION`.** Только аддитивные поля и новые типы; контракт пульта — в своём файле со своей версией.
- **Не паркуем `irreversible` и `order`.** Отложенное удаление файлов, выключение ПК и ордер по устаревшей цене — исполнение в потерянном контексте.
- **Не откладываем произвольные команды.** Нет живого Electron — честный отказ, не очередь.
- **Не даём телефону роль исполнителя.** ActionCommand умеет только сессия Electron; remote — канал восприятия и решения.
- **Не зовём `onOwnerPresent` из remote-канала.** Доклад об инцидентах и сводка дня остаются у ПК.
- **Не пишем свою Noise-стейт-машину** и не используем счётчик-nonce со статичным ключом.
- **Не делаем LLM-реэнтри для исполнения одобренной отправки** — владелец подписал конкретный текст.
- **Не вытесняем pending-одобрения по капу** — durable-обязательство владельца не выбрасывается молча.
