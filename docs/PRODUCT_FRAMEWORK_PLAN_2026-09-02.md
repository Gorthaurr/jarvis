# Каркас продукта Jarvis: пользователи, токены, подписки, безопасность, экономика (2026-09-02)

- Статус: план + расчёт → **реализация начата тем же днём** (раздел 10: что сделано, что открыто). Решения
  владельца, принятые в ходе реализации, — там же; остальные вопросы раздела 8 открыты.
- Метод: 4 проектировщика (экономика; аккаунты/подписки/переключатель; безопасность/риски; облачный мозг +
  LLM-прокси) + 1 критик (противоречия, пропущенные риски, пересчёт чисел, сверка с кодом). Ключевые
  утверждения критика перепроверены вручную по коду. HEAD `9ba4240`. Топология — ADR
  `docs/adr/0001-profile-and-skills-mapping.md` (§1, §2.2, §5.1): продукт с сервером; цель — петля в облаке,
  память/актуаторы на узле пользователя; путь ступенчатый (сначала локальный мозг + LLM-прокси проекта).
- 🔴 Требование владельца: **весь каркас за одним переключателем**; выключен = сегодняшнее поведение
  байт-в-байт, включён = путь пользователя продукта. Раздел 2 — как это гарантируется и где легко нарушить.

## 1. Главные выводы

1. **Экономика упирается не в цену модели, а в форму вызова и хвост распределения.** По реальной
   телеметрии (540 задач, $102,17): средняя задача $0,189, медиана $0,072, верхние 10% задач дают 51%
   расхода. В стоимости вызова Sonnet 60% — запись кеша, из них холодная перезапись 53K-префикса
   (персона + схемы) — 42% всех трат. Переход на Sonnet 5/Opus 5 сам по себе даёт −24% при том же
   токенизаторе и **+2% при токенизаторе ×1,35** — то есть может не дать ничего; замер обязателен до смены тиров.
2. **Главный рычаг (−47% на вызов) — общий тёплый префикс на ключе проекта — сегодня недостижим.**
   `tools[]` собирается per-user/per-session (`agent/index.ts:1413-1437`: промоуты по установленным
   программам, динамические инструменты, MCP-активации), а кеш Anthropic ключуется префиксом
   `tools → system`. Пока набор инструментов не канонизирован в продуктовом режиме, «оптимизированный»
   сценарий — гипотеза, и тарифы нельзя строить на нём. Это первый инженерный инкремент экономики, не
   последний.
3. **All-inclusive за 500–2000 ₽ убыточен** для Average/Heavy при любом сценарии; плоский 2000 ₽ выдерживает
   не больше 1 heavy-пользователя на 7 даже в оптимизированном сценарии. **BYO-key даёт 95–97% маржи**, но в
   РФ «свой ключ» практически означает ключ реселлера (×4 к цене). Рекомендация — **гибрид**: подписка за
   софт 700–1000 ₽ + предоплаченные пакеты «мозга проекта», единица списания — фактическая стоимость
   задачи, не «задача». Пакеты становятся маржинальными только после инкремента 2.
4. **Безопасность продукта — это другая система, не «включить strict».** Почти все рубежи (bind loopback,
   «токен = ключ партиции, не auth», нет TLS, открытые `/stats`/`/cogs`, pre-handshake буфер 4 МБ до
   аутентификации, `action_log` с полными телами команд) написаны для одной машины владельца. Жёсткий минимум
   до первого платящего — 14 пунктов (раздел 6.3), три из них — юридические, не инженерные.
5. **Четыре проекта разошлись в узловых местах** — единица квоты, где авторитетный счётчик, контракт
   прокси, где живёт токен узла, судьба `/dev/*`, STT для РФ, схема БД с ПДн. Разрешено в разделе 3 одним
   решением на каждый пункт; без этого инкременты писались бы под три разных конструкции.
6. **Найденные дефекты кода, вредные уже сегодня** (чинятся без флага, как исправления правильности, с
   реверт-тестами): `pricing.ts` тарифицирует `claude-fable-5-1` в 2× ниже реального и `claude-sonnet-5` в
   1,5× выше (подстрочный матч, `pricing.ts:41-48`; `.env.example` предлагает Fable в TIER3 — свежая
   установка недоучитывает сильный тир вдвое); вкладка «Оплата» печатает доллары со знаком ₽
   (`billing-panel.ts:11`); `cost_estimate NUMERIC(12,2)` округляет каждый раунд до цента (−19% на раунде
   $0,012); `action_log` редактирует только `order.place.items`, а `telegram.send`/`fs.write`/`code.run` пишет
   целиком; резерв на личной подписке владельца конструируется безусловно (`server.ts:189-190`).

## 2. Мастер-переключатель

### 2.1 Один реестр флагов (разрешение расхождений имён)

| Флаг | Значения | Смысл |
|---|---|---|
| `JARVIS_PRODUCT_MODE` | `0` (деф) / `1` | Мастер. `0` = ровно сегодня: dev-token → DEV_USER, без auth/квот/оплаты, `/dev/*` за `JARVIS_DEV_HTTP` |
| `JARVIS_ROLE` | `all` (деф) / `node` / `brain` | Осмыслен только при `1`; при `0` игнорируется молча (не WARN — иначе новая строка лога при 0) |
| Подфлаги (только при `1`, дефолт `true`, выключаются точечно) | `JARVIS_PRODUCT_AUTH`, `_QUOTAS`, `_BILLING`, `_LLM_PROXY`; `_LIBRARY` и `_TELEMETRY` — дефолт `false` | Каждая подсистема отдельно |
| Адреса/секреты | `JARVIS_LLM_PROXY_URL`, `JARVIS_BRAIN_URL`, `JARVIS_BILLING_PROVIDER=yookassa|cloudpayments|none` | Пусто при `1` → честный boot-ERROR + стаб, не падение |
| Токен драйвера | `JARVIS_CLIENT_TOKEN` (деф `"dev"`) | Совпадает с клиентом (`apps/client/main/index.ts:117`); `_jarvis_cmd.mjs:24` перестаёт хардкодить `"dev"` |

Читается один раз в `loadConfig()` в объект `config.product` (`ProductPolicy`); подсистемы читают политику, не
env. Инвариант чистой функции `resolveProductFlags(env)`: **ни один подфлаг не может быть `true` при
мастере `0`** — тест таблицей. Старые `JARVIS_AUTH_STRICT`/`JARVIS_ALLOW_REMOTE`/`JARVIS_CLIENT_IDENTITY`
сохраняют независимый смысл (LAN-режим без продукта законен).

### 2.2 Что мастер форсирует при `1` (нарушение = отказ старта)

Strict-auth **только на облачных ролях** (`brain`, прокси) — на loopback-узле strict театр (`identity.ts:9-14`)
и, хуже, ломает: hello от Electron принимает локальный узел, а device-токены хранит облако → узел отверг бы
собственного клиента 4003 (находка критика). Далее: identity UUID включён; резерв на подписке владельца
**не конструируется** (`FallbackLlmProvider`/`SubscriptionLlmProvider` в `server.ts:185-196`) — boot-ассерт
только по env `CLAUDE_CODE_OAUTH_TOKEN`, файл `~/.claude/.credentials.json` — WARN (иначе продуктовый режим
незапускаем на машине владельца, где файл есть всегда); `ANTHROPIC_API_KEY` на узле при `LLM_PROXY=1`
отсутствует; `/cogs`,`/stats` за `JARVIS_ADMIN_TOKEN`; `JARVIS_LOG_REDACT=1`; `maxPayload` 1 МиБ и
pre-handshake кап 256 КБ на не-loopback bind; `self_*`-инструменты недоступны; `browser_sync_login`
отсутствует в каталоге.

### 2.3 Дефолт `0` = байт-в-байт: где это легко нарушить (критик нашёл семь мест)

Правило: любое изменение поведения при `0` — либо за флагом, либо явно помечено «исправление правильности» с
реверт-тестом и строкой в CLAUDE.md. Известные точки:
- `pricing.ts` версионные тарифы — правильность (меняет `costUsd` только для моделей 5-й серии; 4.6/4.8 фиксируются тестом);
- валюта вкладки «Оплата» — правильность (ложь UI);
- `decision_log`, `/healthz.productMode`, новые файлы на узле — **только при `1`**;
- миграции 0007+ — в отдельный каталог/префикс, который дефолтный `pnpm db:migrate` не применяет; новые
  колонки в запросах (`revoked_at`, `kind`) — только в продуктовой функции, иначе на БД без 0007 strict-путь
  получает SQL-ошибку → `null` → lockout;
- рефакторинги `gatherTurnContext`/`LocalExecutor` — без флага, но с замером латентности хода до/после
  (снимок промпта байт-в-байт не ловит тайминг ретривала 150/2500 мс);
- `/dev/*` при `1` **остаются** (за `JARVIS_DEV_HTTP=1` + loopback + обязательный `JARVIS_DEV_TOKEN`) — иначе
  включённый режим нечем тестировать; добавляются `POST /dev/product/{user,subscription,usage,otp/peek,webhook}`.

### 2.4 Как владелец переключает и тестирует

- **Env + рестарт**, вторым инстансом: `JARVIS_ENV_PATH=.env.product` (`env-path.ts:22-23`), внутри
  `JARVIS_PRODUCT_MODE=1`, `PORT=8797`, `JARVIS_DATA_DIR=…\data-product`, `DATABASE_URL=pglite://…-product`,
  `JARVIS_DEV_HTTP=1`, `JARVIS_SUBSCRIPTION_FALLBACK=0`. Боевой 8787 под супервизором не трогается. Скрипт
  `infra/run-product.ps1` (ASCII-only).
- **vitest**: канарейка `product-mode-off.test.ts` (снимок роутов, 3 ключа `server.hello`, 6 ключей
  `usage.info`, dev-token → DEV_USER) — принимается только если падает при перевороте флага; матрица
  `{0,1}×{подфлаг}` без мутации `process.env` (прецедент `identity.test.ts`); все 11 `*-loop.test.ts` — в обоих
  режимах через `vitest.setup.ts`.
- **Текст-драйвер**: `POST /dev/product/user` → токен → `JARVIS_CLIENT_TOKEN=… JARVIS_WS_URL=ws://127.0.0.1:8797/ws
  node _jarvis_cmd.mjs "…"`. Две поправки драйверу (критик): режим «как живой клиент» (без dev-маркера в
  `clientVersion`, только против тестовой БД — иначе владелец не увидит приветствие/брифинг/ambient, то есть
  именно «путь пользователя») и режим ответа на confirm `approve|deny|ignore` (сейчас авто-approve делает
  все продуктовые гейты «зелёными»).

## 3. Разрешение противоречий четырёх проектов

| Вопрос | Решение | Почему |
|---|---|---|
| Единица квоты | Внутри — **микро-доллары, integer, per round** в `usage_ledger`; агрегат в `usage_quota`; пользователю — «кредиты» (1 кредит = 1 ₽ по курсу периода) + цена каждой задачи в чате/чипе после её завершения | `cost_estimate NUMERIC(12,2)` округляет per-round до цента; «задача» как единица лжёт в 30× (p50 $0,07 … max $2,17); показ цены ПОСЛЕ задачи — закон честности |
| Авторитетный счётчик | **Прокси/облако** (БД проекта). Локальный `SpendGuard` узла — только runaway-кап (шаги/токены на задачу); узел показывает `usage.info` из `GET /v1/usage` | Узел пишет в свою PGlite на диске пользователя (не под self-guard) — не источник истины |
| Контракт прокси | **Ступень 1: passthrough `POST /v1/messages`** + хеш персоны (`offshape` → сниженная квота) + allowlist моделей + кап `max_tokens` + **жёсткая $-квота плана**; **ступень 2: system/tools собирает мозг** | Passthrough не требует правки петли и запускается быстро; ущерб от «бесплатного Claude» ограничен квотой (подпись тела ничего не добавляет — ключ лежит там же, где токен). Решение владельца 8.4 |
| Где живёт токен узла | Отдельный файл `dataDir/node-token` (не `.env`), в `POLICY_BASENAMES` self-guard, `runnerEnv` его не передаёт; провайдер LLM — **ленивая фабрика по токену** (нужна и для BYO per-user) | Локальный мозг — отдельный процесс от Electron и сам ходит в прокси; safeStorage ему недоступен; `.env` читает `code_run` |
| `/dev/*` при `1` | Остаются за `JARVIS_DEV_HTTP=1` + loopback + `JARVIS_DEV_TOKEN` | Требование владельца тестировать включённый режим тем же драйвером |
| STT для РФ-пользователей | Решение владельца 8.6; техническая рекомендация — Yandex SpeechKit через прокси (РФ, без трансграничной передачи аудио), Deepgram — BYO-опция; «локальный whisper при неоплате» **не обещать**, пока не проверен на Windows (onnxruntime CPU-EP «cannot run %1») | 152-ФЗ + непроверенная деградация |
| Схема БД аккаунтов и ЦОД | Решение владельца 8.2; две согласованные конфигурации: (1) email-OTP ⇒ `email_enc` в БД ⇒ ПДн ⇒ РФ-ЦОД/оператор РФ; (2) вход без email (Telegram Login / токен из платёжного провайдера) ⇒ EU-БД без ПДн (`email_hash` только у провайдера) | Проект accounts (email_enc + ip_hash) несовместим с «EU-БД без ПДн» из cloud-brain |
| Профили нагрузки и $/задача | Единая база — телеметрия: Light/Average/Heavy = **90/300/900 задач/мес**, $/задача **$0,189** (все задачи) | Три проекта дали три COGS «Average» ($58/$91/$40) из-за разных баз |
| Холодная запись префикса | **52,7K токенов = $0,316** (Sonnet 4.6, 1h), не «33K/$0,20» | Первый брейкпоинт кеширует tools+персону вместе; 137 холодных записей измерены |

## 4. Экономика (единая база)

Курс 85 ₽/$ (допущение, вилка 80–90). Эквайринг карт 3,5%, СБП 0,6% (допущения по публичным тарифам).

### 4.1 Что измерено

| Метрика | Значение |
|---|---|
| Задач / стоимость | 540 / $102,17 (Sonnet 4.6 ×500 = $73,90; Opus 4.8 ×40 = $28,27 → 7,4% задач = 27,7% денег) |
| Вызовов LLM | 1560 (2,89 на задачу); Opus 8,1% вызовов |

| Владелец | 40,8 задач и $7,73 в активный день (это Heavy-разработчик) |

Не в телеметрии: tier0-ходы и хиты семантического кэша (`metrics.record` только из терминала петли) —

чекпойнта, не «лимит исчерпан»).

### 4.4 Модели монетизации

**BYO-key** (подписка за софт): маржа 94,7% при 500 ₽, 97,4% при 1 000 ₽, 96,9% при $10 (COGS = инфра).
Честная оговорка: РФ-пользователь без зарубежной карты получает ключ реселлера ×4 → его LLM-расход Average ≈
$70/мес; аудитория = те, кто уже платит реселлеру.

**All-inclusive** (ключ проекта), маржа по профилям (без overage):

| Цена | Сценарий | Light | Average | Heavy |
|---|---|---|---|---|
| 1 000 ₽ | (в) | +28% | −134% | −595% |
| 2 000 ₽ | (в) | +64% | −17% | −248% |
| 5 000 ₽ | (в) | +86% | +53% | −39% |
| 2 000 ₽ | (а) | +22% | −155% | −663% |

Задач в месяц, которые покрывает тариф при марже 50%: 1 000 ₽ → 28 (а) / 63 (в); 2 000 ₽ → 58 / 128;
5 000 ₽ → 146 / 323. Heavy при марже 50% стоит ≈ 13 800 ₽/мес (в) и 30 400 ₽ (а). Доля heavy,
обнуляющая маржу плоского 2 000 ₽: 13,8% (в); при 500/1 000 ₽ и $10 маржа отрицательна и без heavy.

**Гибрид (рекомендация)**: подписка за софт 700–1 000 ₽ + предоплаченные пакеты «мозга проекта» (кредиты не
сгорают, overage = следующий пакет, постоплаты нет → нет чарджбэков за «5 000 ₽ непонятно за что»):

| Пакет | Цена | Маржа (в) | Маржа (а) |
|---|---|---|---|
| 50 задач | 900 ₽ | 57% | 6% |
| 100 задач | 1 500 ₽ | 49% | −13% |
| 300 задач | 3 900 ₽ | 41% | −30% |

«Задача» в пакете — расчётная единица (7,4 ₽ средняя), списание — по фактической стоимости. Пакеты
маржинальны только в (в) → **сначала инкремент общего префикса, потом пакеты**. На 1 000 пользователей
(60/30/10): BYO 1 000 ₽ → маржа ~97% при ограниченной конверсии; all-inclusive 2 000 ₽ → 12% до overage и 0%
при 14% heavy; гибрид (700 ₽ + пакет у 40%) → ~75% (доля покупателей — допущение).

### 4.5 Чувствительность (blended, $/мес)

| | База | Цена моделей +30% | −30% | Opus-эскалации ×2 | 20% heavy |
|---|---|---|---|---|---|
| (а) | 45,3 | 58,6 | 32,0 | 57,1 (+26%) | 60,9 (+34%) |
| (в) | 20,8 | 26,7 | 14,8 | 26,4 (+27%) | 27,8 (+34%) |

Самый опасный фактор — состав пользователей (один heavy = 9,6 light), второй — токенизатор Sonnet 5. Выводы:
квота в стоимости, Opus-эскалация §7 гейтится планом (Light — только Sonnet, честный нудж «сильная модель

## 5. Каркас аккаунтов, токенов, подписок, квот

### 5.1 Идентичность и auth (подфлаг `PRODUCT_AUTH`)

- `users` += `email_hash` (HMAC с pepper из мастер-ключа), `role user|admin`, `status active|blocked|deleted`,
  `deleted_at`, `trial_used_at`; `email_enc` — только в конфигурации (1) раздела 3. Колонка `email` plaintext
  (0001:19) в продукте не пишется.
- `auth_tokens` += `kind device|access|refresh`, `device_id`, `revoked_at`, `rotated_from`, `ip_hash`; таблица
  `devices` (0001:214, не используется) += `install_id`, `name`, `revoked_at`.
- Токены **opaque + sha256 в БД** (прецедент 0003), префиксы `jdt_`/`jat_`/`jrt_` для secret-scanner'ов и
  роутинга в резолвере ДО проверки `isUuid` (`identity.ts:56`). Device 365 дн со скользящей ротацией через
  `server.hello.rotatedToken`; access 1 ч; refresh 30 дн one-time с отзывом семьи при повторном использовании.
- Вход: **email + одноразовый код** через собственный `smtp.ts` (три исхода, `SmtpUncertainError` → «код,
  возможно, ушёл — запросите новый»), 6 цифр, TTL 10 мин, 5 попыток; пароль — опция (`scrypt` из
  `node:crypto`, без нативных зависимостей; argon2id только через prebuilt `@node-rs/argon2`); Telegram Login —
  опция вторым способом (и путь для конфигурации без email).
- Rate-limit — собственный token-bucket (в зависимостях нет `@fastify/rate-limit`): OTP 5/ч на email, 20/ч на
  IP, verify 5 попыток, login 30/ч на IP; плюс **второй таймер на сам `doHandshake`** (10 с) и кап соединений на
  IP — сейчас таймер снимается при первом hello и длительность резолва ничем не ограничена при живом 4 МБ буфере.
- Удаление/экспорт (152-ФЗ/GDPR): `DELETE /v1/me` → tombstone + отзыв всех токенов + отложенный purge 30 дн
  (каскады `ON DELETE CASCADE` уже в 0001/0003); `GET /v1/me/export`; данные узла принадлежат пользователю
  (вкладка «Память» + копия `data/`). Admin: `role=admin`, bootstrap `JARVIS_ADMIN_EMAILS`, `/v1/admin/*`
  (list/grant/kill/purge); `kill_switch` оживает как durable-колонка `usage_quota`.

### 5.2 Подписки и оплата (подфлаг `PRODUCT_BILLING`)

- Таблицы `plans` (seed `trial|byo|basic|pro`, цифры — решение владельца), `subscriptions` (статусы
  `trialing|active|past_due|canceled|expired`, partial UNIQUE одной живой подписки), `invoices`, `payments`,
  `webhook_events(provider,event_id PK)` — идемпотентность `ON CONFLICT DO NOTHING`, обработка в транзакции.
- Провайдер за интерфейсом `PaymentProvider {createCheckout, verifyWebhook, parseEvent, cancelRecurring}`;
  первый — один (ЮKassa или CloudPayments, решение 8.3), только hosted-checkout, карт в системе нет (§0-p5).
  Сумму/статус перечитывать по API провайдера, не из тела вебхука.
- Жизненный цикл: регистрация → `trialing` без карты (один триал на `email_hash` и `install_id`) → оплата →
  `active` → неоплата → `past_due` с grace 7 дн (голосом раз в день, retriable) → `expired` = **деградация, не
  отключение**: квота проекта 0, узел работает на tier0 + BYO-key; память/профиль/напоминания нетронуты; голос
  при неоплате — честно «недоступен», пока whisper на Windows не проверен.

### 5.3 Метеринг и квоты (подфлаг `PRODUCT_QUOTAS`)

- `usage_ledger(user_id, ts, task_id, round, model, in/out/cr/cc, cost_micro_usd INT, stt_sec, tts_chars,
  channel node|proxy|brain, estimated BOOL)` — пишется на каждый раунд (прокси — из `usage` ответа, для стрима
  `message_start` + `message_delta.usage`; обрыв стрима → оценка консервативно вверх с `estimated=true`).
  Агрегат — `usage_quota` (+ `llm_quota_usd`, `overage_allowed/max`, `soft_pct`, `warned_80/100_at`,
  `quota_source`; мёртвые `spend_cap`/`kill_switch`/`tts_chars_used` оживают).
- `QuotaResolver.limitsFor(userId)` читается один раз в `hydrate` (уже в handshake) → `SpendGuard.setLimits`;
  `check()` остаётся синхронным; пороги 80/100% → `usage.info` push + голос один раз (durable `warned_*`);
  100% без overage → `deny("spend_cap")` → честный терминал «кредиты тарифа исчерпаны — продлить или добавить
  свой ключ», не «связь прервалась» (`anthropic.ts` различает 402 `quota_exceeded`).
- Резерв на задачу: `check()` сегодня оценивает раунд в $0,01 (`agent/index.ts:2301`) → перерасход до максимума
  одной задачи; для квоты плана — резерв p95 ($0,82) на старте или разрешённый овердрафт одной задачи.
- `UsageInfo` += `unit:"credits"`, `credits{quota,used,remaining,pct}`, `planId`, `status`, `periodEnd`,
  `overage`, `warn`; вкладка «Оплата» рисует кредиты, топ-5 дорогих задач месяца, кнопку checkout
  (`shell.openExternal`); `TaskStatus.costRub` в таск-чипе §20.

### 5.4 Протокол и API

WS остаётся версии 1 — только аддитивные поля: `Hello += installId, deviceName, capabilities`; `ServerHello +=
productMode, user{id,planId,status}, rotatedToken`; `ProtocolError.code += login_required | subscription_required |
device_revoked` (новый клиент на них не реконнектится — расширить `transport/index.ts:469`). HTTP на облачной
роли (при `enabled && role!=="all"`, кроме `/v1/meta`): `/v1/meta`, `/v1/auth/{otp/request,otp/verify,refresh,

## 6. Безопасность и риски

### 6.1 Границы доверия продукта

Узел ↔ сервер проекта: сервер **не доверяет узлу** (любой локальный процесс говорит от его имени; attestation
не рубеж, а удорожание обхода — ущерб ограничивает только квота + отзыв); узел доверяет серверу по TLS с
пином. Пользователь A ↔ B: через общие артефакты (библиотека навыков, рецепты сайтов — только подписанные с
сервера, промоут = заявка в ревью, в промпте без слова «проверенный»), через prompt-cache (безопасно: кеш
хранит только идентичный префикс; правило — ничего идентифицирующего в кешируемых блоках, инвариантный тест
`buildSystemBlocks` для двух пользователей), через БД (RLS — к ступени 2).

## 7. Облачный мозг и LLM-прокси

### 7.1 Ступень 1 — прокси при локальном мозге (S/M, ≈2–3 недели)

`AnthropicLlmProvider` уже принимает `baseUrl` и кладёт `apiKey` в `x-api-key` (`anthropic.ts:42-44, 297-310`) →
мозг не меняется; все фоновые LLM-потребители узла (watch-чекер, сон-цикл, рефлексы, эксперт, префилл)
переезжают автоматически. Прокси (`apps/llm-proxy`, standalone вне workspace, по образцу relay): auth
sha256-токена fail-closed, allowlist моделей, кап `max_tokens ≤ 16 000`, `temperature/top_p/top_k` → 400, хеш
персоны → `offshape`, SSE pass-through без буферизации (иначе `PhraseSpeaker` теряет смысл), проброс
`anthropic-beta` (1h-кеш), ретрай только до первого байта, upstream-таймаут ≥ клиентского (170 с), метеринг в
ledger, 402 по квоте, `/metrics`. Накладные +30–80 мс на вызов (+1–4% к TTFT 1,8–4,4 с). TTS — через прокси
(REST, метеринг символов); STT — решение 8.6.

**Обязательный инкремент экономики на этой ступени: канонический `tools[]` + `systemTools` в продуктовом
режиме** (промоуты/динамические/MCP — в per-user блок после брейкпоинта или в каталог) + тест-инвариант «два
userId → байт-идентичные tools и system[0..1]» + живой замер cache_read на двух пользователях одного ключа.
Без него сценарий (в) и пакеты не работают.

### 7.2 Ступень 2 — облачная петля (XL, семь инкрементов)

Разрез не «весь dispatch», а два шва: (1) `gatherTurnContext` — чистый вынос сбора контекста хода
(`agent/index.ts:1295-1403`: retrieval, recall, профиль, задачи, паспорт, `client.env/system`) в `TurnContext`;
(2) `LocalExecutor` в `ToolContext` — server-side кейсы, трогающие состояние пользователя (`memory_*`, `skill_*`,
`reminder_*`, `watch_*`, `obligation_*`, `calendar/mail_read`, `mail_send`, `telegram_*`, `consent_*`,
`app_channel_*`, dyn-tools, MCP, `tinkoff_portfolio`), уходят через `ctx.local.exec` → в dev это in-process
исполнитель тех же хендлеров (поведение байт-в-байт), в облаке — `ActionCommand` на узел. В мозге остаются:
петля, персона/кеш, каскад тиров, verify/анти-капитуляция, `tool_load`, `web_search/fetch`, `knowledge`,
`market_*`, §14-гейты как политика (вопрос владельцу задаёт узел, `ConfirmOutcome` возвращается). Голос —
целиком на узле. Сеансовая модель — один WS `/node` от узла, **stateful-воркер, sticky по соединению**,
чекпойнты событиями `checkpoint.save` на узел (stateless-петля с Redis — не строим). Reconnect — зеркало
`transport/index.ts` с интернет-параметрами relay (бэкофф 1→60 с, outbox, дедуп). Ёмкость ≈ 300 узлов на
2 vCPU/4 ГБ (допущение). ЦОД — решение 8.2. Инкременты 6–7 (`gatherTurnContext`, `LocalExecutor`) — чистые
рефакторинги под существующими loop-тестами, можно делать сразу.
